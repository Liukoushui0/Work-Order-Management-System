## 2. 简历可直接使用的写法

### 2.1 一句话版本（项目列表用）

> **ServiceFlow 企业售后工单管理系统**（Java 17 / Spring Boot 3 / Vue 3 / MySQL / Redis）：面向售后团队的全流程工单系统，实现工单状态机、三层权限校验、并发保护、运营统计与缓存、附件安全与操作审计，后端 163 个自动化测试全部通过。

### 2.2 两句话版本（项目描述栏用）

> 面向设备售后团队的工单管理系统，覆盖「客户报修 → 建单 → 分派 → 接单 → 维修处理 → 客户确认 → 评价 → 运营分析」全流程，含客户/设备档案、RBAC 权限、附件管理与操作审计。
> 后端采用模块化单体架构（Spring Boot 3 + MyBatis-Plus + MySQL + Redis），前端为 Vue 3 + Element Plus 单页应用；通过状态机与条件更新保证工单流转一致性，用 Redis 做统计缓存与并发锁，并以三层权限校验防止越权访问。

### 2.3 亮点式 bullet（推荐写法，每条 1~2 行）

- **工单状态机与并发保护**：设计 6 种工单状态与 10 类流转动作（含退回、转派、退回重做、重新打开），用「状态 + 版本号」条件更新 + Redis 分布式锁 + 数据库唯一索引三层保证一致性；并发接单测试中 4 线程仅 1 次成功，重复操作返回明确业务码而非脏数据。
- **并发建单死锁的定位与重构**：发现"查询当日最大编号 + 唯一索引重试"在 MySQL 默认 REPEATABLE READ 隔离级别下会读到同一快照，导致重试风暴并触发死锁；改为独立序列表原子取号（`INSERT ... ON DUPLICATE KEY UPDATE`），消除重试并保证编号全局唯一。
- **三层权限校验体系**：接口级注解鉴权 + 资源级关系校验（工单负责人/所属客户）+ 数据域自动收敛（工程师仅见本人、客户仅见自身），并针对"修改 URL/ID 越权"编写集成测试，越权请求统一返回 403 与明确错误码。
- **发现并修复事务导致的安全缺陷**：登录失败计数若与登录流程同事务，业务异常回滚会让计数永不生效、账号锁定形同虚设；改为独立事务（`REQUIRES_NEW`）写入计数与锁定状态，并补充集成测试验证"连续失败 5 次后锁定"。
- **Redis 缓存的工程化落地**：统计结果按数据范围隔离缓存键（`all` / `u{userId}`）避免跨用户串数据，设置 60/300/600 秒分级 TTL，写操作在**事务提交后**失效缓存防止并发读回填旧数据，并实现 Redis 不可用时的自动降级（单元测试覆盖该路径）。
- **附件上传下载安全**：扩展名与大小白名单由系统配置驱动，原始文件名清洗 + UUID 存储名 + SHA-256 摘要，下载前先校验工单访问权限再做路径规范化校验（拒绝目录穿越），删除时同步清理物理文件并对失败落盘做补偿。
- **审计与可观测性**：基于 AOP 的操作审计切面记录关键操作（含失败请求），参数自动脱敏，traceId 通过 MDC 贯穿日志与响应头，便于按请求定位问题。
- **前端工程化与性能优化**：抽象设计令牌（CSS 变量）统一卡片/表格/菜单观感，按角色生成菜单与路由守卫，ECharts 图表全部使用后端真实统计；通过 `manualChunks` 与路由懒加载把主包从 1.1 MB 降至 51 KB（gzip 21 KB），ECharts 仅在图表页面加载。
- **测试体系**：后端用 Surefire/Failsafe 分层（单元测试不依赖外部服务、集成测试连接真实 MySQL 与 Redis），覆盖状态机矩阵、越权、数据隔离、并发接单、并发建单、评价条件、附件权限、统计数值与缓存失效；前端用 Vitest + Vue Test Utils 覆盖渲染、表单校验、接口异常与路由权限。
- **工程规范与交付**：分 10 个阶段推进，每阶段"开发 → 测试 → 审查 → 提交 → 合并 → 双远程同步 → 汇报"，54 个规范提交，并产出 11 份文档（需求计划、技术设计、数据库设计、API 文档、部署排查、测试报告、验收与安全审查、Git 工作流、简历素材等）。

## 3. 技术难点详解（面试讲深度的素材）

以下每条都按 **问题 → 分析 → 方案 → 结果** 组织，可直接口头复述。

### 3.1 并发建单：从死锁到原子取号

- **问题**：并发建单测试（5 线程）失败，出现 `DuplicateKeyException` 连续 4 次重试后抛 `Deadlock found when trying to get lock`。
- **分析**：原本采用"查询当日最大编号 + 1，插入，唯一索引冲突则重试"。在 MySQL 默认的 REPEATABLE READ 下，**同一事务内重复执行 `SELECT MAX(...)` 始终读取事务开始时的快照**，并发事务会反复算出同一个编号，形成重试风暴，进而在唯一索引上互相等待造成死锁。
- **方案**：新增序列表 `ticket_sequence(seq_date, current_value)`，用 `INSERT ... ON DUPLICATE KEY UPDATE current_value = current_value + 1` 在同一行上原子自增取号，再读取本事务写入的值；唯一索引仍作为兜底约束保留。
- **结果**：5 线程并发建单编号互不重复、无重试无死锁；代价是取号瞬间对当日序列行加锁至事务提交，对本系统建单频率完全可接受（已在设计文档记录取舍）。

### 3.2 工单状态机与幂等

- **设计**：6 状态（待分派、待接单、处理中、待确认、已完成、已取消）+ 集中式转换矩阵，特殊流转包括退回、转派（回到待接单需重新接单）、客户退回重做、重新打开（受完成时间窗口限制）、取消（终态不可再变）。
- **一致性**：每次流转用 `WHERE id=? AND status=? AND version=?` 条件更新，影响 0 行时再读一次区分"状态已被他人改变"（1402/1403）与"版本冲突"（1602），避免把并发冲突误报成业务错误。
- **可追溯**：所有流转写入处理记录（操作人、角色、前后状态、内容、工时），详情页以时间线展示完整历史。
- **测试**：单元测试覆盖转换矩阵（主流程/特殊流转/非法跳转/终态），集成测试覆盖"待分派直接接单被拒""待接单直接完成被拒""取消后不可操作"等真实场景。

### 3.3 三层权限校验（防越权）

- **接口级**：`@PreAuthorize` + 30 项权限编码（4 角色 / 65 条授权），权限来自"用户 → 角色 → 权限"三级查询。
- **资源级**：`AccessGuard` 在 Service 层校验操作人与资源的关系（例如"是否为该工单的当前负责人/所属客户"），防止通过修改 URL 或 ID 越权。
- **数据域级**：`DataScopeService` 为列表查询自动附加范围条件，工程师只查分配给自己的工单、客户只查自身数据；统计接口同样按范围收敛（全局 / 仅本人），客户角色直接 403。

### 3.4 事务边界导致的"计数永不生效"

- **问题**：登录失败锁定功能在集成测试中始终不触发。
- **分析**：登录方法标注了 `@Transactional`，失败时抛出业务异常会**回滚同一事务内的失败计数更新**，计数永远停留在 0。
- **方案**：把失败计数与锁定、以及登录成功后的计数清零抽到独立事务（`@Transactional(propagation = REQUIRES_NEW)`）的服务中，使其不受登录业务回滚影响。
- **结果**：连续 5 次密码错误后账号锁定，正确密码也被拒绝（返回 1003），已有集成测试守护。

### 3.5 缓存一致性

- **键设计**：`sf:{env}:{module}:{name}:{scope}`，`scope` 区分全局（`all`）与按用户（`u{userId}`），避免把"某工程师的个人统计"当成全局结果返回给他人。
- **失效时机**：写操作通过 `TransactionSynchronization#afterCommit` 在**事务提交后**清理缓存，避免"缓存已删、事务未提交"期间被并发读请求用旧数据回填。
- **降级**：缓存读写全部包裹异常处理，Redis 不可用时按未命中处理直接查库（写操作 WARN 提示），分布式锁不可用时退化为数据库条件更新，业务不中断；该路径有单元测试覆盖。

### 3.6 附件与文件访问安全

| 风险 | 措施 |
| --- | --- |
| 上传可执行文件 | 扩展名白名单由 `sys_config` 驱动，非白名单返回 1503 |
| 超大文件 | 大小上限同样配置驱动（默认 20MB），超限返回 1504 |
| 文件名注入 / 覆盖 | 原始名清洗（去目录、去控制字符、限长），存储名使用 UUID，按 `ticket-{id}/{yyyy-MM}` 分目录 |
| 目录穿越 | 下载时用"基准目录 + 规范化路径"双重校验，越界即拒绝；单元测试覆盖 `../`、绝对路径、Windows 分隔符等取值 |
| 越权下载 | 先校验工单访问权限（负责人 / 所属客户 / 客服 / 管理员），附件 ID 与工单不匹配返回 1505 |
| 数据完整性 | 落盘失败不入库、入库失败删除已落盘文件；删除附件同时逻辑删除元数据并清理物理文件 |
| 文件完整性 | 上传时计算 SHA-256 入库，集成测试断言与源文件一致 |

### 3.7 依赖与环境的真实问题定位（体现排障能力）

- **Element Plus `el-tag` 空指针**：仪表盘状态标签报 `Cannot set properties of null (setting 'bum')`，通过阅读库源码定位到挂载钩子 `vnode.component.subTree.component.bum = null` 缺少判空，升级到修复版本后消失（升级前后用单元测试对比验证）。
- **Logback 1.5 配置不兼容**：Spring Boot 3.3 使用 Logback 1.5，已移除 `SizeAndTimeBasedFNATP`，原日志配置导致上下文启动失败，改用 `SizeAndTimeBasedRollingPolicy`。
- **Redis `MISCONF` 静默拒绝写**：实例 RDB 持久化失败时所有写命令被拒（`PING` 仍正常，极易误判为"Redis 正常"），通过 `redis-cli info persistence` 定位，改为以安装目录为工作目录并用 `--dir` 指定可写目录后恢复，并在文档中记录排查方法。
- **npm 缓存目录权限**：全局缓存目录对当前用户只读导致 `EPERM`，改用项目内缓存并记录。

### 3.8 前端工程化与性能

- **设计与代码分层**：颜色/圆角/阴影/间距统一为 CSS 变量并对齐 Element Plus 变量；公共观感（卡片、表格、菜单、标签、滚动条、页面切换动画）在全局层统一，页面只写业务样式。
- **权限体验**：菜单按角色过滤、路由守卫做未登录与无权限跳转，但前端只负责体验，所有权限仍由后端强制校验。
- **数据可视化**：ECharts 封装为通用组件，图表数据全部来自统计接口，无硬编码数字；支持按日/周/月切换趋势粒度。
- **体积优化**：`manualChunks` 拆出 vue / Element Plus / ECharts，结合路由懒加载，主包由 1.1 MB 降至 51 KB（gzip 21 KB）。

## 5. 面试高频追问与回答要点

| 追问 | 回答要点 |
| --- | --- |
| 工单状态为什么这样设计？ | 状态对应售后真实节点（待分派=等客服、待接单=等工程师、处理中、待确认=等客户确认、已完成、已取消）；特殊流转来自真实场景：工程师退回、客服转派、客户不满意退回重做、完成后短期内重新打开、建错单取消。 |
| 并发接单怎么保证只有一个人成功？ | 三层：Redis `SET NX EX` 锁降低冲突 → 「状态 + 版本号」条件更新保证只有一次能改成功 → 数据库分派记录唯一索引兜底；失败方拿到明确错误码（1403/1402/1602），并通过 4 线程并发用例验证。 |
| 为什么用序列表而不是自增 ID 或 UUID 做单号？ | 业务要求单号可读（日期 + 当日序号）、唯一且不能暴露业务量；UUID 不可读，自增 ID 会泄露总量，序列表可精确控制格式并支持并发原子取号。 |
| 乐观锁和悲观锁怎么选？ | 工单流转读多写少、冲突概率低，选乐观锁（版本号 + 条件更新）避免长时间持锁；取号场景冲突集中在一行，直接利用数据库行锁原子自增更简单可靠。 |
| 缓存怎么保证不脏？ | 键含数据范围避免串数据、写操作在事务提交后精确失效、TTL 兜底、Redis 不可用降级查库；不缓存用户凭据与附件内容。 |
| 越权怎么防？ | 三层校验（接口级/资源级/数据域）+ 集成测试覆盖"改 ID 访问他人数据""跨客户查询""非负责人操作"等场景，前端隐藏按钮不作为安全手段。 |
| 测试怎么保证是"真的"？ | 集成测试连接真实 MySQL 与 Redis 并通过 HTTP 接口驱动业务；断言状态码与业务码、查询数据库落地结果；并发用例用线程池 + 起跑闩；测试数据用 `it_` 前缀并在用例后清理。 |
| 为什么前端不用 TypeScript？ | 按个人取舍选择 JavaScript（ES2022），用 JSDoc 与 ESLint 承担类型提示与规范检查；若团队要求类型安全可平滑迁移，接口结构已通过 `types`/JSDoc 集中描述。 |
